# Planora

Самостоятельно размещаемый планировщик проектов с диаграммой Ганта: категории,
задачи, сроки, критичность и история изменений с отменой. Организация — единица
изоляции данных; регистрация свободная, первый вошедший получает собственную
организацию и роль `owner`.

Этот файл — подробное руководство по развёртыванию, эксплуатации и разработке
(бэкапы, почта, приглашения, публикация в интернет, Vercel, тесты). Короткий
обзор продукта со скриншотами — в [README.md](README.md).

## Запуск

Из зависимостей нужен только Docker с плагином `compose` — ни Python, ни Node
на машине ставить не нужно, всё собирается внутри образов.

```sh
git clone https://github.com/aspacev1/planora.git
cd planora
cp .env.example .env      # отредактируй APP_SECRET, DIRECTOR_EMAIL и учётные данные Postgres
docker compose up --build
```

Первый запуск занимает несколько минут: собираются образы бэкенда и фронтенда,
поднимается Postgres и накатывается схема. Дальше `docker compose up` стартует
за секунды. Остановка — `docker compose down`: данные живут в томе `pgdata` и
остановку переживают. Команда `docker compose down -v` — не «остановка
получше», а снос установки вместе с базой, безвозвратный; если она зачем-то
понадобилась, сначала убедись, что в `./backups` лежит свежий дамп (раздел
«Резервное копирование»).

Интерфейс открывается на <http://localhost:8080> — там регистрация, вход и
список проектов. Порт меняется переменной `WEB_PORT` в `.env`, если 8080 уже
занят.

Других портов обычный запуск на хосте не занимает: ни базы, ни бэкенда наружу
нет — между собой они общаются по внутренней сети compose, а снаружи всё
доступно через тот же 8080. Занятый локальным Postgres 5432 или чужой uvicorn
на 8000 запуску больше не мешают. Заглянуть внутрь можно через контейнеры:
`docker compose exec db psql -U planora`, `docker compose logs -f api`.

Фронтенд и API живут за одним доменом: Caddy отдаёт статику с корня, а всё,
что начинается с `/api/`, проксирует в бэкенд. Это не украшательство —
сессия хранится в HTTP-only куке, и на двух разных доменах браузер её просто
не сохранил бы. По той же причине адреса вроде `/projects` отдают
`index.html`: маршруты живут на клиенте, файлов под них нет, и без этого
перезагрузка страницы внутри приложения давала бы 404.

Отсюда же и API: проверка живости — <http://localhost:8080/api/health>.
Отдельным портом бэкенд открывается только в режиме разработки (ниже). Схема
базы накатывается автоматически (`alembic upgrade head` выполняется перед
стартом сервера), отдельного шага миграции нет.

Программно: `POST /api/auth/register` с полями `name`, `email`, `password`
ставит куку сессии, и с ней доступны `POST /api/projects`,
`GET /api/projects/{id}` и `POST /api/projects/{id}/mutations`.

Открытый проект держит живую связь `WS /api/projects/{id}/live` с той же
кукой: применённые кем-то ревизии приходят в неё сами, и вкладки соседей
обновляются без перезагрузки. По этому сокету ничего не принимается — менять
проект можно только мутацией по HTTP. Рассылка живёт в памяти процесса, так
что приложение рассчитано на один процесс; второй потребовал бы общей шины.
Когда связь рвётся, интерфейс говорит об этом полоской «нет связи, показаны
данные на 14:32» и запирает редактирование до восстановления, а восстановив,
перезапрашивает проект целиком — пропущенное не доигрывается.

## Резервное копирование

Дампы снимает сервис `backup` из `docker-compose.yml` — тем же образом
`postgres:16`, что и сама база, поэтому версии `pg_dump` и сервера не
расходятся. Раз в сутки он кладёт в `./backups` на хосте файл вида
`planora-20260811-031500.dump` (сжатый формат `pg_restore -Fc`) и удаляет
дампы старше двух недель. Расписание и глубина хранения меняются переменными
`BACKUP_INTERVAL_SECONDS` и `BACKUP_KEEP_DAYS` в `.env`. Каталог `./backups`
лежит вне томов Docker намеренно: бэкап обязан переживать
`docker compose down -v`. Он же — то, что стоит забирать с машины наружу
(rsync, объектное хранилище), если установка не одноразовая.

Восстановление из дампа:

```sh
docker compose stop api            # чтобы никто не писал в базу под ногами
docker compose exec -T db pg_restore -U planora -d planora \
  --clean --if-exists < backups/planora-20260811-031500.dump
docker compose start api
```

Бэкап, который ни разу не восстанавливали, — это лотерейный билет, а не бэкап.
Раз в месяц (и после каждого изменения схемы) проверяй свежий дамп
восстановлением во временную базу — процедура не трогает рабочие данные:

```sh
docker compose exec db createdb -U planora restore_check
docker compose exec -T db pg_restore -U planora -d restore_check \
  < backups/planora-20260811-031500.dump
# счётчики должны быть похожи на правду, а не нули
docker compose exec db psql -U planora -d restore_check \
  -c 'select count(*) from users' -c 'select count(*) from tasks'
docker compose exec db dropdb -U planora restore_check
```

## Работа с лентой

Лента — не картинка плана, а способ его править: почти всё, что меняет сроки,
делается прямо на ней, без карточки задачи.

**Задачи заводятся строкой, а не окном.** «Плюс» на строке категории (или
«Новая задача» в тулбаре) открывает в конце категории поле: написали имя,
нажали `Enter` — задача создана, поле опустело и ждёт следующую. Так план
пишется списком, не отрываясь от клавиатуры. Пустой `Enter` закрывает строку,
`Esc` закрывает и не сохраняет, уход фокуса сохраняет набранное.

Спрашивается только имя. Новая задача начинается сегодня — или в начале своего
этапа, если этап ещё впереди, — и занимает один рабочий день. Всё остальное
(описание, исполнители, связи, критичность, веха, заметка) правится в карточке,
которая открывается щелчком по задаче, и на самой ленте.

**Строка под курсором обведена и показывает своё.** Обвод идёт по верхнему и
нижнему краю во всю ширину — и таблицы, и шкалы: полоска задачи уезжает от
своего названия на месяц вправо, и линия соединяет их глазом. Вместе с ним
проявляется то, что до сих пор жило только в карточке:

- **счётчик обсуждения** — число реплик у задачи. Если разговор есть, число
  видно всегда, а не только под курсором; щелчок открывает карточку сразу на
  вкладке «Комментарии»;
- **исполнители** — аватары назначенных, а у ничьей задачи «Назначить».
  Щелчок раскрывает состав организации, и люди сажаются на задачу по одному,
  не открывая карточку. Кнопка стоит в колонке «Исполнитель», когда та
  показана, и в колонке имени, когда нет;
- **«плюс» на верхней границе строки** — завести задачу прямо здесь, между
  двумя соседними. Поле открывается на этом месте, и созданная задача встаёт
  туда же: сосед и все, кто ниже, съезжают на строку. Это одна операция, а не
  «создать в конце и переставить», — то есть одна запись в истории и одно
  нажатие «Отменить».

Ни один из этих знаков не нужен, чтобы дойти до того же с клавиатуры: разговор
и исполнители лежат в карточке задачи, до которой один шаг с полоски, а задача
заводится «плюсом» на строке категории. Поэтому шагами `Tab` они строку не
удлиняют — как и ручка перестановки рядом.

| Жест | Что меняется | Что уходит на сервер |
| --- | --- | --- |
| Тянуть полоску | обе даты разом | `move_task` |
| Тянуть левую грань | начало; конец на месте | `resize_task` |
| Тянуть правую грань | длительность | `set_duration` |
| Тянуть границу заливки | процент выполненного, с шагом 5 | `set_progress` |
| Тянуть от кружка на краю к другой полоске | связь | `add_dependency` |
| Тянуть сводную полосу категории | весь этап целиком | `move_category` |
| Тянуть ручку `⠿` слева от задачи | порядок задач, в том числе перенос в другой этап | `reorder_task` |
| Тянуть ручку `⠿` слева от категории | порядок этапов | `reorder_category` |
| «Плюс» на границе строк | новая задача на этом месте | `create_task` с `position` |
| Выбрать человека в списке исполнителей | назначение | `assign_user` / `unassign_user` |

Кружки связи появляются на краях полоски при наведении на строку — а на
сенсорном экране, где наведения не бывает, по касанию самой полоски. Правый
означает «эта задача блокирует ту, на которую бросили», левый — обратное.
Кольцо сервер не пропустит и объяснит отказ словами.

Пока строку несут, её имя едет за курсором полупрозрачной плашкой, а сама она
гаснет на своём месте: и то, и другое означает «перенос ещё не случился».
Категорию гасит целиком, вместе с задачами, — переезжает она тоже целиком.
Целятся при этом в строку под курсором: линия по её краю показывает, куда
строка встанет, заливка заголовка — что задачу кладут в этот этап. Категория
целится только в заголовки, поэтому бросок на строку задачи означает её этап.

Начатый жест прерывается по `Esc`. Доведённый до края ленты подкачивает её —
перенести задачу с марта на июнь можно одним движением.

С клавиатуры полоска умеет то же, что и под указателем:

| Сочетание | Что делает |
| --- | --- |
| `Shift + ←→` | перенести задачу |
| `Alt + ←→` | растянуть конец |
| `Shift + Alt + ←→` | двинуть начало, конец на месте |

Голые стрелки оставлены прокрутке ленты: без этого нельзя было бы просто
посмотреть, что справа, не сдвинув при этом сроки. Всё то же правится и полями
— в таблице слева и в карточке задачи, — так что ни один жест не является
единственным способом что-то изменить.

**Вехи** — точки на шкале вместо отрезков: сдача этапа, согласование, дедлайн
подрядчика. Рисуются ромбом, длительности не имеют (сервер держит её равной
одному дню) и граней не получают, но двигаются и связываются как обычные
задачи. Признак ставится флажком «Веха» в карточке задачи.

**Таблица слева** — колонки «Начало», «Окончание», «Длительность», «Готово» и
«Исполнитель». Набор переключается меню «Колонки», ширины тянутся за границы
заголовков (или стрелками, когда граница в фокусе), а сами колонки
переставляются местами перетаскиванием за заголовок. Имя задачи с первого
места не уходит: это единственная колонка, по которой строка опознаётся.

Правится щелчком по ячейке всё, включая окончание, — но окончание правится не
собой, а длительностью: настоящую дату считает сервер по рабочему календарю
проекта, а ячейка переводит названный день в число рабочих дней тем же счётом,
каким это делает правая грань полоски. Набор колонок, их порядок и ширины
запоминаются в браузере для каждого проекта отдельно — как и масштаб.

## Связи: картинка или расписание

По умолчанию связь — стрелка на картинке: даты по ней не пересчитываются.
Задача, наехавшая на своего блокировщика, рисуется стрелкой наискось, и лента
предлагает подвинуть её одной кнопкой — предлагает, а не двигает.

Рубильник «Автоперенос по связям» в настройках проекта меняет это правило:
последователь больше не начинается раньше, чем кончился его предшественник.
Сервер двигает цепочку сам — при переносе задачи, при растягивании её грани,
при сдвиге категории и при появлении новой связи.

Двигает **только вперёд**. Задача, между которой и её предшественником остался
запас, назад не подтягивается: запас в плане чаще всего поставлен нарочно —
приёмка, отпуск, окно поставки, — и автоперенос, вычищающий такие промежутки,
переписывал бы план, которого никто не просил переписывать.

Вся цепочка уезжает одной операцией и одной записью в истории: отмена
возвращает её целиком, одним нажатием. Порог объяснений при этом считается по
самой правке, а не по её последствиям — иначе один и тот же вопрос задавался бы
столько раз, сколько в проекте связей.

**Критический путь** — слой в меню «Вид»: цепочка задач, у которых нет запаса,
обводится по контуру вместе со стрелками между ними. Сдвинь любую из них на
день — на день уедет окончание проекта. Запас считает сервер рабочими днями по
календарю проекта.

## Показать проект наружу

Проект открывается по ссылке вида
`https://домен/p/<слаг-организации>/<слаг-проекта>?s=<токен>`: слаги — то, что
человек читает, токен — то, что делает отзыв ссылки осмысленным. Владелец или
редактор выпускает её кнопкой «Публичная ссылка» на экране проекта
(`POST /api/projects/{id}/share`), там же выключает комментарии и
перевыпускает адрес — прежний умирает мгновенно.

Гость видит ту же диаграмму, что и команда, но **без внутренних заметок и без
исполнителей**, и не может ничего изменить. Комментировать может, если
комментарии включены: при первой реплике он вводит имя, оно запоминается в
браузере и подписывает его сообщения пометкой «гость». Гостевые реплики
приходят команде в ту же ленту проекта.

По ссылке ходит не только клиент, поэтому в шапке страницы есть вход. Гостю она
предлагает «Войти» и после входа приводит в этот же проект на рабочий экран, а
не в общий список; тому, кто уже вошёл, — «Открыть в приложении». Чужому
аккаунту проект отвечает обычным отказом: ссылка открывает страницу, а не
доступ к проекту внутри.

Домен ссылки берётся из `PUBLIC_BASE_URL` — не из заголовков запроса, иначе
адрес однажды уедет клиенту с чужим доменом. Публикацию можно запретить на всю
установку рубильником `PUBLIC_SHARING_ENABLED=false`: уже выданные ссылки
закрываются вместе с выпуском новых.

### Свой домен и TLS

Из коробки установка слушает голый HTTP на 8080 — это годится для localhost и
для сети за своим обратным прокси, но не для установки, открытой в интернет:
кука сессии и пароли не должны ходить открытым текстом. Простейший путь —
тот же Caddy, который уже раздаёт интерфейс: замени в `Caddyfile` адрес
`:8080` на свой домен (`plan.example.com {`), выведи наружу порты 80 и 443
вместо `WEB_PORT` — и Caddy сам выпустит и будет продлевать сертификат
Let's Encrypt.

Привилегированные порты при этом занимает Docker на хосте, а не Caddy внутри
контейнера: там он работает не от root и без единой capability (`USER web`,
`cap_drop: [ALL]`, `no-new-privileges`), то есть сесть на 80 и 443 сам не
может и не должен. Значит, наружу они пробрасываются на высокие порты
контейнера, а Caddy предупреждается об этом глобальными настройками — иначе
он будет ждать ACME-проверку и слать редирект не туда:

```yaml
# docker-compose.yml, сервис web
ports: ["80:8080", "443:8443"]
```

```caddy
# Caddyfile, до блока сайта
{
	http_port 8080
	https_port 8443
}
```

Эти два порта — «внутренние»: клиентам Caddy по-прежнему называет 80 и 443,
на которых его и видно снаружи.

В `.env` при этом задай `PUBLIC_BASE_URL=https://домен`:
из него собираются ссылки в письмах и публичные адреса, а кука получает флаг
`Secure` (он же выводится из `X-Forwarded-Proto`, а на особый случай есть
явный `COOKIE_SECURE`). Если TLS терминирует другой прокси перед Caddy,
убедись, что он передаёт `X-Forwarded-Proto: https` — либо задай
`COOKIE_SECURE=true` руками.
## Почта

Из коробки почта выключена (`MAIL_TRANSPORT=none`), и это рабочая установка, а
не недонастроенная: письмо целиком уходит в журнал приложения
(`docker compose logs -f api`) — оттуда при локальной разработке и берётся
ссылка подтверждения. Включается одной переменной:

| `MAIL_TRANSPORT` | Что нужно задать |
|---|---|
| `none` | ничего; письма остаются в журнале, кнопки отправки нет |
| `log` | ничего; письма остаются в журнале, но кнопка отправки на месте |
| `smtp` | `SMTP_URL`, `MAIL_FROM` |
| `api` | `MAIL_API_URL`, `MAIL_API_KEY`, `MAIL_FROM` |

Основной вариант — SMTP: он работает с любым провайдером, включая собственный
сервер. `smtps://` шифрует соединение с самого начала, `smtp://` переходит на
STARTTLS, если сервер его предлагает; пароль по незашифрованному каналу не
передаётся вовсе — такая отправка отменяется с записью в журнал. Транспорт
`api` шлёт `{from, to, subject, text}` на адрес рассылочного сервиса (форма
Resend и совместимых с ним). Приложение не стартует, если транспорт выбран, а
нужные ему переменные пустые.

Письма уходят синхронно, в том же запросе, и неудачная отправка не отменяет
действие: регистрация состоится и без письма, а ссылку подтверждения можно
запросить заново — `POST /api/auth/verify-email/resend` (ответ честно говорит
`{"sent": false}`, если письмо не ушло). Между письмами держится минута, и
считается она от ушедшего письма, а не от выданного токена: за письмо, которого
почта не приняла, ждать нечего. Сама ссылка гасится через
`POST /api/auth/verify-email` с токеном из письма: она одноразовая, живёт сутки
и сессии не требует — почту читают не обязательно в том же браузере. Открытая
повторно, погашенная ссылка отвечает `{"already_verified": true}`, а не
отказом: по ссылке из письма ходят дважды — сначала почтовый сканер, потом
человек, — и второй заход должен рассказывать про подтверждённый адрес.

Неподтверждённый адрес видно в самом приложении: над содержимым висит полоска
с адресом и кнопкой «отправить письмо ещё раз», а сразу после регистрации она
говорит, на какой адрес письмо ушло. Подтверждение при этом ничего не
запрещает: в установке без почтового сервера `email_verified_at` остаётся
пустым у всех, и это не должно мешать работать — полоски там нет вовсе.

Тексты писем лежат по файлу на язык в `backend/app/mail/templates/`; письмо
уходит на языке адресата, отсутствующий ключ откатывается на язык установки с
предупреждением в журнал. Полнота словарей проверяется тестом.

## Приглашения

Позвать людей в организацию можно на экране «Участники». Владелец вводит
адреса (можно несколько сразу), выбирает роль и, для любой из них, — отмечает
проекты, к которым сразу даёт доступ. Отметка сужает приглашение до этих
проектов, независимо от роли: у «клиента» без отметок доступа не будет ни к
одному проекту, у «редактора» и «наблюдателя» без отметок сохраняется
поведение по умолчанию — вся организация сразу. Дальше два равноправных пути:
отправить письмо и скопировать ссылку. Второй — не запасной вариант на случай
поломки почты: письма теряются в спаме, а половина рабочей переписки живёт в
мессенджерах. **Без настроенной почты установка остаётся полноценной** — просто
кнопки отправки в ней нет, а ссылка копируется как обычно.

Приглашение одноразовое, живёт `INVITE_TTL_DAYS` дней и несёт роль, которую
принимающий подменить не может. Отозвать неиспользованное можно в любой момент —
ссылка умирает сразу. «Новая ссылка» выпускает новый токен и убивает прежний:
иначе отозвать то самое отправленное письмо было бы нечем.

**Ссылка показывается один раз** — в момент выпуска. Второй раз её взять негде,
потому что сервер её не помнит: в базе лежит только хеш токена, как у пароля.
Размен сознательный: хранение токена в расшифровываемом виде экономит один клик
и превращает утёкший дамп базы в набор действующих ключей от всех организаций.

Число приглашений в час на организацию ограничено `INVITE_RATE_LIMIT`. В потолок
идут создание приглашения и отправка письма по нему; выпуск ссылки для
копирования — нет, письма при нём не уходит.

Принявший приглашение оказывается в позвавшей организации. Если своя у него уже
была, обе доступны из переключателя в шапке; выбор живёт до конца сессии.

Позвать того, кто уже в организации, нельзя: выпуск отвечает `already_member`.
Приём такого приглашения всё равно ничего бы не изменил — роль действующего
членства он не трогает, — но выглядел бы действием, и зовущий ждал бы человека,
который внутри со вчера.

Роль «владелец» приглашением не выдаётся вовсе (`role_not_invitable`), и держит
это правило сервер, а не спрятанная строка выпадающего списка. Причина в том,
что приглашение без адреса достаётся предъявителю: владельцем становился бы
всякий, кто открыл переславшуюся ссылку. Владельца назначают действующему
участнику — поимённо и отдельным действием (ниже).

Программно: `POST /api/org/invitations` (`emails`, `role`, `project_ids`,
`deliver`) выпускает приглашения и возвращает ссылки, `GET /api/invitations/{token}`
показывает, куда зовут, `POST /api/invitations/{token}/accept` принимает.

## Состав организации

Роли четыре, и под выбором каждой написано, что она даёт: по умолчанию
«наблюдатель» видит все проекты организации, а «клиент» — только те, куда его
позвали поимённо. Отметка проектов при приглашении (см. выше) сужает до них
любую роль, не только клиента, — узнавать об этом после отправки приглашения
поздно, поэтому список проектов виден в форме сразу.

Владелец меняет роль участника прямо в строке состава и выводит человека из
организации. Роль применяется сразу по выбору — она обратима тем же списком;
вывод спрашивает, потому что обратим только новым приглашением. Поимённые
доступы к проектам уходят вместе с членством, а назначения на задачах остаются:
снять их можно и потом, а стирать исполнителя со всех его задач в ответ на
кадровое решение значило бы молча переписать план.

Уйти самому можно из того же экрана — «Покинуть организацию». Прав в
организации это не требует: роль «клиент» не видит даже её состава, и если бы
уход требовал права, позванный однажды остался бы внутри навсегда.

**Последнего владельца не разжаловать и не вывести** — ни чужими руками, ни
своими (`last_owner`). Организация без владельца не разжалована, а заперта
навсегда: назначить в ней нового больше некому. Чтобы уйти последним владельцем,
сначала назначают владельцем кого-то ещё.

Программно: `PATCH /api/org/members/{user_id}` (`role`) меняет роль,
`DELETE /api/org/members/{user_id}` выводит из организации. Второй маршрут же —
и «покинуть»: со своим собственным идентификатором он не требует прав, потому
что действие одно и то же, а разными их делает только то, кто его выполняет.

## Панель директора

По адресу `/admin` живёт список всех аккаунтов установки: имя, адрес, дата
регистрации, организации, в которых человек состоит, и когда он в последний
раз пользовался продуктом. Видит её не тот, кто завёл организацию, а тот, кто
эксплуатирует установку целиком, — роль «директор».

Директор — не то же самое, что роль «владелец» состава организации выше: та
существует внутри одной организации, и владельцев организаций в установке
может быть сколько угодно. Директор — единственная роль уровня всей
установки, и он один. Её адрес задаёт переменная окружения `DIRECTOR_EMAIL` —
обязательная, без значения по умолчанию: приложение не стартует, если её не
задали, тем же способом, что и с `APP_SECRET`. Роль переносится правкой
`.env` (или секрета платформы) и перезапуском — без изменений в коде.
Сравнение адресов идёт той же нормализацией, что и уникальность аккаунта при
регистрации, — регистр и совместимые формы юникода роли не играют.

```
DIRECTOR_EMAIL=owner@example.com
```

Пункт «Админ-панель» в колонке приложения виден только директору; остальным
сервер отвечает `403 forbidden` — тем же кодом и тем же баннером отказа, что и
на любом другом закрытом маршруте.

«Последняя активность» — не то же самое, что запись сессии: строки сессий
подметаются (выход, просрочка, недельный простой без обращений), и список
сессий человека, годами не заходившего снова, со временем пустеет целиком.
Момент последней активности поэтому хранится отдельным полем на самом
аккаунте (`users.last_active_at`) и переживает эту уборку.

Программно: `GET /api/admin/users` отдаёт список, отсортированный по дате
регистрации — новые сверху.

## Публикация на Vercel

Docker-раскладка выше остаётся основной для самостоятельного размещения;
Vercel — второй способ, ничего в ней не отменяющий. Разница в том, что база
данных на Vercel не живёт: платформа отдаёт статику и поднимает функции, а
Postgres нужен внешний (Neon, Supabase, любой другой управляемый — подойдёт
любой, до которого дотягивается сеть).

Раскладка описана в `vercel.json` и повторяет однодоменный расклад Caddy:
`frontend/dist` отдаётся с корня, `/api/*` уходит в одну serverless-функцию
`api/index.py` (тонкий мост к тому же `app.main`, что и под compose), а
остальные адреса падают на `index.html` — маршруты по-прежнему живут на
клиенте. Сессия остаётся в HTTP-only куке на том же домене, поэтому CORS не
нужен и здесь.

1. Создай проект на Vercel из этого репозитория. Root Directory — корень, не
   `frontend`: в корне лежат и `vercel.json`, и `api/`. Framework Preset —
   `Other`. Настройки сборки задавать не нужно, они уже в `vercel.json`.
2. Подключи базу: в проекте вкладка **Storage** → Neon (или заведи её на
   стороне и вставь строку подключения руками). Бери адрес **через пулер** —
   у Neon и Supabase это адрес со словом `pooler`. Обычный тоже соединится,
   но функций под нагрузкой поднимается много, и каждая займёт своё
   соединение: лимит сервера кончится раньше трафика.

   Строку можно вставлять как есть, в том виде, в каком её даёт панель:
   драйвер `+psycopg` дописывается сам (`backend/app/config.py`).
3. Пропиши переменные окружения проекта. `.env` в бой не едет и не должен —
   на Vercel их источник только настройки проекта:

   | Переменная | Значение |
   | --- | --- |
   | `DATABASE_URL` | строка из шага 2, если её не вписала интеграция |
   | `APP_SECRET` | длинная случайная строка, не из `.env.example` |
   | `DIRECTOR_EMAIL` | адрес, которому будет видна панель директора (`/admin`) |
   | `DEFAULT_LOCALE`, `SUPPORTED_LOCALES`, `SIGNUP_MODE` | по вкусу, умолчания в `backend/app/config.py` |
   | `MAIL_TRANSPORT` и переменные под него | см. «Почта»; без них письма остаются в журнале функции |

   Секрет сгенерируй, а не придумывай: `openssl rand -hex 32`.

   `PUBLIC_BASE_URL` задавать не нужно — он выводится из домена, который
   выдала платформа. Из него берётся флаг `Secure` у куки сессии, а домен до
   первого деплоя неизвестен, и требовать его заранее означало бы деплой,
   потом значение, потом деплой заново — с незащищённой кукой в промежутке.
   Задай его, только когда привяжешь свой домен: его платформа в своих
   переменных не показывает.
4. Деплой.
5. Накати схему. Автоматического `alembic upgrade head` перед стартом, как в
   compose, здесь нет и быть не может: функция поднимается на запрос, и
   миграция в этот момент — гонка между параллельными холодными стартами.
   Один раз с машины разработчика, тем же адресом базы, что в настройках
   проекта:

   ```sh
   cd backend
   DATABASE_URL='postgresql://…' APP_SECRET=любая DIRECTOR_EMAIL=любая \
     uv run alembic upgrade head
   ```

   `APP_SECRET` и `DIRECTOR_EMAIL` здесь нужны только чтобы прошла проверка
   настроек; в базу они не попадают. Повторять после каждой новой ревизии в
   `backend/migrations/versions`.

Проверка: `curl https://<домен>/api/health` отвечает `{"status":"ok"}`.

Зависимости функции перечислены в корневом `requirements.txt` — сборщик
Python читает только его и про `backend/pyproject.toml` с `uv.lock` не знает.
Меняешь зависимости бэкенда — поправь оба файла: расхождение версий ловит
тест `test_vercel_requirements_match_uv_lock`, так что CI не даст бою молча
собраться со старым набором.

Preview-деплои поднимаются на каждый push в ветку с открытым PR, а переменные
окружения у них те же — значит, **и база та же, что у прода**. Это не
теоретическая тонкость: preview-ветка с новой миграцией накатит её на боевую
базу, а эксперименты в интерфейсе preview читают и пишут настоящие проекты
настоящих клиентов. Правильная раскладка — вторая база (у Neon/Supabase это
бесплатная ветка): задай `DATABASE_URL` отдельно для окружения Preview в
настройках Vercel, и прод перестанет быть полигоном.

Штатные `/docs` и `/redoc` от FastAPI на Vercel недоступны: они лежат вне
`/api/`, и фолбэк на `index.html` перехватывает их раньше функции. Схема
по-прежнему доступна локально.

Живых обновлений на Vercel не будет: WebSocket требует процесса, который живёт
дольше запроса, а serverless-функция поднимается на запрос. Интерфейс это
замечает сам — сокет не открывается ни разу, живая лента молча выключается, и
экран продолжает работать как обычный: изменения уходят по HTTP, чужие правки
видно после перезагрузки. Полоска «нет связи» при этом не показывается и
редактирование не запирается: она означает оборванную связь, а не её
отсутствие. Кому живые обновления нужны, тому нужна docker-раскладка.

## Разработка в контейнерах

Обычный запуск запекает код в образы: правка файла ничего не меняет, пока не
пересоберёшь. Наложение `docker-compose.dev.yml` монтирует рабочую копию с
хоста, и оба сервера следят за файлами сами — uvicorn с `--reload`, интерфейс
на Vite вместо статики за Caddy.

```sh
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build
```

Адрес прежний — <http://localhost:8080>, и `/api` там проксирует уже Vite, а не
Caddy. Правка `.tsx` видна в браузере сразу, правка Python перезапускает
сервер. Пересборка нужна только при смене зависимостей: после правки
`package.json` — с `--renew-anon-volumes web`, иначе в контейнере останется
старый `node_modules`.

Образ бэкенда в этом режиме ставит и dev-зависимости, поэтому тесты можно
гонять прямо в контейнере, без Python на хосте:

```sh
docker compose exec api pytest
```

В этом же режиме на хост выводятся Postgres (`DB_PORT`, по умолчанию 5432) и
бэкенд (`API_PORT`, по умолчанию 8000) — для тестов и psql снаружи, для `/docs`
и curl по адресам API, а ещё для `npm run dev` на хосте: его прокси смотрит
именно на `localhost:8000`. Если порты заняты, задай другие в `.env`; вместе с
`DB_PORT` поправь порт и в `DATABASE_URL` — тесты берут адрес оттуда.

## Разработка интерфейса без Docker

```sh
cd frontend && npm install && npm run dev
```

Dev-сервер поднимается на <http://localhost:5173> и проксирует `/api` на
`http://localhost:8000` — тот же однодоменный расклад, что и в бою. Бэкенд по
этому адресу нужно чем-то занять: либо своим uvicorn, либо контейнером из
режима разработки (обычный запуск api наружу не выводит). Если он слушает на
другом порту, адрес задаётся переменной `API_TARGET`.
Тесты интерфейса — `npm test` в `frontend/`; они бьют по перехваченной сети,
базы и бэкенда им не нужно.

`.env` — единственный источник настроек, и в `.env.example` каждая описана
комментарием. Три значения обязательны и не имеют умолчания: `DATABASE_URL`,
`APP_SECRET` и `DIRECTOR_EMAIL`.

## Оформление

Интерфейс собран по дизайн-системе Notion. Вся палитра, типографика, радиусы
и тени живут переменными в одном файле — `frontend/src/styles.css`; тема
Northstar (`frontend/src/northstar-theme.css`) переопределяет только их, и ни
один компонент об этом не знает. Остальные файлы стилей (`gantt.css`,
`panel.css`, `comments.css`, `live.css`) берут цвета оттуда и своих значений
не заводят.

Три правила, из которых выведено остальное:

- **Бумага, а не панели.** Фон один и тот же почти везде, части разделяют
  расстояние и линия в 9% чернил. Рамка вокруг каждого блока дробит экран на
  отсеки и мешает читать подряд.
- **Интерфейс молчит, пока к нему не обратились.** Кнопки строк, ручки
  перетаскивания, действия приглашений проявляются при наведении и фокусе. На
  доступность это не влияет: видимость не меняет доступное дерево, и с
  клавиатуры они есть всегда.
- **Цвет — знак, а не украшение.** Синий значит «действие», красный —
  «просрочено», зелёный — «в срок». Заливку получает одно действие на экран;
  остальные кнопки приглушённые (`button--quiet`). Всё прочее набрано
  чернилами разной плотности.

Навигация — боковая колонка (`components/Header.tsx`), страница рядом с ней
(`auth/RequireAuth.tsx`). Уже `900px` колонка ложится сверху строкой.
Публичная страница проекта колонки не имеет вовсе: у гостя нет ни разделов,
ни профиля, и там своя тонкая шапка (`.header`).

## Тесты

Тесты работают только с базой `<имя из DATABASE_URL>_test` и никогда с базой
из `DATABASE_URL` — `backend/tests/conftest.py` это проверяет и отказывается
запускаться иначе. Эта база создаётся сама при первом запуске Postgres
(`docker/postgres-init/10-create-test-db.sh`), отдельного шага нет.

С хоста они ходят в базу по адресу из `DATABASE_URL`, то есть требуют, чтобы
Postgres был выведен наружу, — это делает наложение для разработки:

```sh
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d db
cd backend && uv run pytest
```

Без Python на хосте те же тесты идут внутри контейнера — `docker compose exec
api pytest` (см. «Разработка в контейнерах»).

Если том `pgdata` появился раньше этого скрипта, Postgres его уже не выполнит —
такую базу нужно создать один раз руками:

```sh
docker compose exec db createdb -U planora planora_test
```
